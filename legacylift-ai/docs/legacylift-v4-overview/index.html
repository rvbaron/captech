What shipped into LegacyLift v4

Since v3.7.0 in April, LegacyLift stopped being a documentation generator with a web front end and became a modernization platform: a deterministic code index underneath, Anthropic's code-modernization plugin as the workflow spine, and business requirements stored as queryable records with a review lifecycle instead of markdown that the next run overwrites. It shipped as v4.0.0 on 2026-09-15.

Why the test count matters more than the line count

The engine is deterministic infrastructure that an LLM then reasons over. Determinism is only a claim until it is pinned: the 1,280 tests run against a polyglot fixture repository with a hash-based embedder, so the whole suite runs offline and a regression in chunking, graph resolution or requirement identity fails the build rather than surfacing in a client deliverable. As of v4.0.0 that is enforced rather than remembered — a tests.yml CI job runs the suite on every pull request to main, alongside dotnet build and ng build for the review surface.

02  /  Foundation

What changed at the foundation

v3 was a set of Claude Code skills that read a repository and wrote markdown documents, fronted by a web application. v4 replaced all of it: that front end is gone — a new read-only review surface took its place (§08) — and so is the reliance on those skills. In their place are a deterministic index of the code and Anthropic's code-modernization plugin as the sequence a modernization engagement actually follows. v4 derives everything it needs from the source repository and its own index — it does not call the v3 skills, read their output, or fall back to them.

The two are therefore separate offerings, and an engagement runs one or the other. v4 is the accuracy option: it produces the most accurate and most detailed requirements reverse engineering available, and it costs more to run and asks more of the estate — /modernize-preflight is what checks whether those prerequisites are met. v3.7 remains the lower-cost option, yielding fewer requirements in less depth, for clients who cannot or do not want to meet those prerequisites, or who would rather spend less than get the most accurate result. It ships as the legacylift-classic plugin and is self-contained: it needs no index and no data store.

The plugin is Apache-2.0 from Anthropic, and v4.0.0 made that traceable rather than implied. Nine files in our copy carry a CapTech modification line recording what we changed and when; the pristine upstream LICENSE ships unmodified beside CapTech's own terms and a root NOTICE; .claude-plugin/.upstream records the upstream commit this fork came from; and a test fails the build if the duplicated licence copies drift.

03  /  Process

Assess, decide, then one of three pathways

Modernization programmes fail in a predictable way: transforming code before anyone understands it, or shipping without a harness that would catch behaviour drift. The v4 workflow makes that sequence explicit, and it makes the method a decision rather than an assumption. Four discovery commands produce reviewable artifacts; the brief turns them into a plan a steering committee approves; only then does code get written, by one of three different methods.

Where the commercial value sits

Discovery is the part a client can buy on its own and review before committing to a rebuild: four commands, each producing a standalone artifact with file:line citations. The approval gate between discovery and build is deliberate — it is where a steering committee makes a decision with evidence rather than with a vendor's estimate.

04  /  Engine

Layer 0: the code index

Layer 0 is the part of v4 that did not exist before: a Python CLI that builds a local, deterministic index of a legacy repository and answers questions about it without an LLM in the loop. It exists because keyword search has three structural limits — it cannot find conceptually related code that shares no token with the query, it produces a noisy call graph, and its sense of "have we looked everywhere?" is a guess.

The pipeline, stage by stage

StageWhat it does
Discovery Walks the repository against 28 include patterns and 22 exclusions, hashes every file with SHA-256, and classifies language and third-party status against a vendored GitHub Linguist profile (833 languages, 1,486 extensions, 419 filenames, 55 vendor directory patterns, 113 vendor filename patterns).
Extraction tree-sitter grammars per language for symbols and references, with a regex fallback path for COBOL. 15 languages are registered. Later milestones added annotations, SQL column facts and type references as first-class facts.
Chunking Symbol ranges first — a chunk is a function or class, not an arbitrary window. If symbol chunks cover under 30% of a file, fall back to AST-aware chunking, then to line windowing. Seven languages are hard-blocked from the AST chunker after measured hangs (a 13.9 KB JSP ran past 600 seconds).
Embedding Three interchangeable providers: a deterministic hash embedder for tests, a local Qwen3 model, and hosted Amazon Bedrock Titan v2 at 1,024 dimensions — the production path, because the local model runs at roughly 350 ms per chunk on CPU, an 80-minute job on this corpus.
Code graph Caller/callee edges resolved by qualified then plain name, each scored: 0.85 one candidate, 0.70 same-language ambiguity, 0.40 cross-file ambiguity, 0.30 unresolved. Unresolved edges are kept with the callee name rather than dropped. Edge kinds: calls, inherits, implements, references, uses_table.
Retrieval SQLite FTS5 lexical search and Chroma vector search, fused with reciprocal rank fusion. Plus a coverage command that turns "loop until two rounds find nothing new" into a chunk-level measurement of what has not been examined.
05  /  Scope

What is actually in scope

An index silently omits what it does not recognise, and so does every tool that counts lines of code. That is a quiet, expensive failure mode: rule extraction measures its own completeness as a fraction of indexed chunks, so an index that never saw the presentation layer will certify itself complete while having no view of it at all. The layer0-extraction-gap-detection work exists to make the unknown reportable.

How the walk decides

  • Linguist for classification, never for filtering. The vendored profile answers "what language is a .tld file?" and "is this path third-party?" It is used to classify and rank findings. Filtering on it would reproduce the exact failure being fixed.
  • One provenance rule, one place. A shared module makes file discovery and the gap walk apply the same third-party rules, so the two can no longer disagree about what counts as our code.
  • Symbol-dead is not out of scope. Of the eight new patterns only XML yields symbols. The other seven contribute retrieval coverage as text chunks reachable by both search arms — which is what the extraction lenses actually consume.
Open item this created, recorded rather than buried

Admitting **/*.properties pulled in 15 files carrying cleartext credentials, including a production one. Indexing them locally was a deliberate call; the caveat is that hosted embedding sends their contents off the machine regardless. The design questions are written up as a pending draft rather than left implicit.

06  /  Domains

Capability domains, and code attached to them

Before v4, domain knowledge existed in two weak forms: namespace prefixes inferred bottom-up, or a markdown table an LLM wrote that no tool could query. Eight milestones shipped in July made capability domains a first-class, durable relation — every file assigned to exactly one domain, in a database that survives re-indexing.

CapabilityHow it works
Capture /modernize-assess now emits a machine-readable domains.json — per-domain path globs, inter-domain dependency edges, and exclusions — alongside the human-readable assessment.
Association tag-domains resolves globs to files, writes the assignment, and stamps the domain onto every vector so the semantic arm can filter on it. On the reference corpus: 1,504 files resolved — 1,120 glob-matched, 384 excluded, 0 unassigned — across 12 domains and 36 edges, stamping all 15,398 chunks.
Human edits win A hand-corrected assignment is marked manual and is never overwritten by automatic re-tagging, including on a full re-index.
Honest coverage An excluded tier distinguishes "deliberately out of scope" from "nobody has classified this yet" and drops it from the denominator. The reference application went from a reported 69% to an honest 100%.
Diagram render-architecture generates the architecture diagram deterministically from the domain catalog and its edges — byte-identical from either the database or domains.json, and no longer hand-authored by a model.
Freshness validate reports a distinct domains axis that goes loud when new, unclassified files appear, so a stale classification is visible instead of assumed.
07  /  Requirements

Requirements as data, not prose

This is the largest single body of work in v4, and the one with the clearest commercial edge. Extraction used to end in a markdown file: run it again and every human correction, sign-off and rejection was gone, and nobody could answer "which rules touch the Orders table?" or "how many rules has anyone actually approved?" without reading thousands of lines by hand.

v4 replaces the file with a store. Each rule becomes a record with a stable identifier, citations back to the exact lines it was mined from, a review lifecycle, and a notation strict enough to validate. Re-running extraction merges into the store, so human review accumulates instead of evaporating. Markdown becomes a report generated from the store.

The notation: one sentence, decomposable

The sentence form composes two standards: the ISO/IEC/IEEE 29148 requirement skeleton supplies the slots, and OMG SBVR supplies the modal keyword, selected by whether the rule is behavioral or definitional. Ten closed patterns cover both classes. Every deviation from the standards is recorded in a numbered register rather than quietly taken.

What the record carries

42 columns on the requirement itself, plus 14 companion tables for citations, scenarios, edge cases, validator findings, computed data flow, merge candidates and run metadata. The fields that matter for how the product behaves:

FieldValuesWho fills it
statedraft · reviewed · approved · rejected · supersededA named human. No automated producer can move a record out of draft.
rule_classbehavioral · definitionalExtractor, by a deterministic procedure. Never guessed — NULL is an extraction failure and blocks approval.
modalityrequirement · expectationExtractor proposes, an SME confirms; the proposal and the confirmation are stored separately.
enforcement_levelstrict · deferred · pre-authorized · post-justified · override · guidelineSME only — the manual half of enforcement is not in the repository, so it is not derivable from code.
structured_bodydecision_table · state_transition · formula · invariantExtractor, schema-validated. A decision table is data, not a paragraph describing one.
as_built vs statement—What the code does is recorded separately from what the business requires, so a suspected defect can be flagged instead of laundered into a requirement.
rationale · fit_criterion—SME only, extractor forbidden. An empty field is review progress, not a defect.

Identity, and why re-running is safe

The guarantee that makes the store usable is that running extraction twice produces the same count the second time, not double. Each rule gets a dedupe key derived from its citation anchors, class, pattern and body; a second run merges onto existing records and queues anything ambiguous for a reviewer rather than deciding silently.

The commands a reviewer actually uses

Fourteen subcommands under legacylift-search requirements. The four that define the product: list --state approved answers the question nobody could answer before; set-state records a human judgement and refuses to reach approved while any ERROR finding stands; validate reports notation violations without changing anything; export --format jsonl writes a git-committable file so a team can review requirement changes in a pull request.

08  /  Surface

The review surface, read-only by design

A requirements store is only worth building if someone other than its author can read it. platform-ui, new in v4.0.0, is a web view over everything v4 produces for a system: requirements with server-side paging, full-text search and facets; every citation resolved to the lines the rule was mined from; merge candidates awaiting a decision; topology, capability domains, diagrams and the generated documents. It is read-only, and that is a decision rather than a shortfall — the store owns the approval gate and every write path, so this milestone proves the corpus is legible before anything is allowed to change it. Where a write would go, it shows what the store holds and says so.

What this milestone did not include

There are no tests for either half yet — Milestone 1 had no test scope, and the Angular scaffold's vitest setup is what forces npm install --legacy-peer-deps on this machine. CI builds both halves on every pull request, which catches a break but proves nothing about behaviour. It is now a tracked deliverable with a measured starting point rather than a footnote.

09  /  Evidence

The research basis

The notation was not invented. Twenty survey threads went through the requirements-engineering and business-rule-extraction literature; thirteen primary sources were acquired and read directly rather than summarised second-hand. The survey's most useful negative finding: the field's published extraction work mostly emits "code snippets or graph slices," not normative requirement sentences — which is precisely the gap v4 occupies.

Licensing is tracked per source. The OMG specifications are freely redistributable and safe to quote; the ISO copy on hand is a third party's institutional download, so a CapTech-licensed copy is an open action before any client deliverable quotes it.

The honest number on evaluation

The survey looked hard for an oracle and did not find one: there is no accepted ground truth for "the business rules in this codebase," so no extraction tool can report recall. That is why v4 reports coverage against the index instead, and why the review lifecycle exists — the measurable claim is "a named human approved this rule against these cited lines," which is a stronger thing to hand a client than a confidence score.

What to take away

v4 moved LegacyLift from "an LLM reads your code and writes documents" to "a deterministic index and a reviewed requirements store, with an LLM doing the judgement work in between." The difference a client can see: citations that resolve, coverage stated as a number with its denominator, a re-run that preserves their reviewers' work, and a recommendation between uplift, transform and reimagine that is backed by a delta catalog rather than a preference.
