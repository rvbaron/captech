# LegacyLift v4.0.0 — Release Notes

**Released:** 2026-09-15 · **Previous release:** `v3.7.0` (2026-04-23) · **285 commits**

LegacyLift v4 is a different product from v3.7, not a newer version of it. v3.7 was a set of
Claude Code skills that read a repository and wrote markdown, fronted by a web application. v4 is a
**modernization platform**: a deterministic code index underneath, Anthropic's
`code-modernization` plugin as the workflow spine, and business requirements stored as **queryable
records with a review lifecycle** instead of markdown the next run overwrites.

Both versions ship from this repository and an engagement runs **one or the other**. v4 shares no
component with v3.7 and does not call its skills.

---

## Highlights

### 1. A deterministic code index (Layer 0) — new, from nothing

`tools/legacylift_search/` is a local Python CLI that indexes a legacy repository and answers
questions about it **with no LLM in the loop**: hybrid semantic + lexical retrieval fused by
reciprocal rank fusion, a confidence-scored code graph, and coverage reported as a measured
percentage of chunks rather than a guess.

- **Discovery** — 28 include patterns, 22 exclusions, SHA-256 per file, language and third-party
  classification against a vendored GitHub Linguist profile (833 languages, 1,486 extensions).
- **Extraction** — tree-sitter per language (15 registered), regex fallback for COBOL; annotations,
  SQL column facts and type references are first-class facts.
- **Chunking** — symbol-range first (a chunk is a function or class, not an arbitrary window), with
  AST-aware and line-window fallbacks. Seven languages are hard-blocked from the AST chunker after
  measured hangs.
- **Embedding** — three interchangeable providers: a deterministic hash embedder for tests, local
  Qwen3, and hosted Bedrock Titan v2 at 1,024 dimensions (the production path).
- **Code graph** — caller/callee edges scored 0.85 / 0.70 / 0.40 / 0.30; **unresolved edges are
  kept with the callee name** rather than dropped.

### 2. Human judgment survives a re-index — the Layer 0 / Layer 1 split

The load-bearing design decision of v4. Machine-derived facts (`index.sqlite` + Chroma) are cheap
and rebuildable; a reviewer's sign-off is not. They live in **different databases**, and only one of
them can be thrown away: `index --reset` rebuilds Layer 0 and stops at that boundary, leaving every
domain assignment, approved requirement and review note in `knowledge.sqlite` untouched.

### 3. Requirements as data, not prose

The largest single body of work in v4. Extraction used to end in a markdown file — run it again and
every correction, sign-off and rejection was gone.

- **One sentence, decomposable.** The notation composes ISO/IEC/IEEE 29148 (the requirement
  skeleton) with OMG SBVR (the modal keyword). **Ten closed patterns** across two rule classes
  (4 behavioral, 6 definitional), with a database constraint tying each pattern to its class.
- **The record carries 42 columns** plus 14 companion tables — citations, scenarios, edge cases,
  validator findings, computed data flow, merge candidates, run metadata.
- **No automated producer can approve a requirement.** `ingest` writes `draft`; `set-state` requires
  a named human and refuses `approved` while any evaluated `ERROR` finding stands. 28 validator
  rules; `WARN` never blocks.
- **`as_built` is recorded separately from `statement`** — what the code does versus what the
  business requires, so a suspected defect can be flagged instead of laundered into a requirement.
- **Re-running merges, it does not replace.** Each rule gets a dedupe key from its citation anchors,
  class, pattern and body; a second run merges and queues anything ambiguous for a reviewer. On the
  reference corpus the second and third ingests of the same file each reported
  **0 new · 437 merged · 0 candidate** and inserted zero rows.
- Markdown is now a **report rendered from the store**, not the store.

### 4. Capability domains as a first-class, durable relation

Eight milestones replaced "namespace prefixes, or a markdown table nothing could query."

- `/modernize-assess` emits a machine-readable `domains.json` — per-domain globs, inter-domain
  dependency edges, and exclusions.
- `tag-domains` resolves globs to files and **stamps the domain onto every vector**, so the semantic
  arm can filter on it.
- **Hand-corrected assignments are marked `manual` and are never overwritten**, including on a full
  re-index.
- An **`excluded` tier** distinguishes "deliberately out of scope" from "nobody has classified this
  yet" and drops it from the denominator — the reference application went from a reported 69% to an
  honest 100%.
- `render-architecture` generates the architecture diagram **deterministically** from the domain
  catalog, byte-identical from either the database or `domains.json` — no longer hand-authored by a
  model.

### 5. What is out of scope is now reportable

An index silently omits what it does not recognise, and rule extraction measures its own
completeness as a fraction of indexed chunks — so an index that never saw the presentation layer
would certify itself complete. Measured on the reference corpus: **276 files and 805 KB of
first-party source had never been opened, 178 of them JSP — the entire presentation layer.** Eight
new file patterns, seven language registrations and a shared provenance module closed it for 4.4%
more index wall clock. File discovery went from **1,229 to 1,504 files**.

Linguist is used to **classify, never to filter** — filtering on it would reproduce the exact
failure being fixed.

### 6. An enforced workflow, with a human gate before any code is written

```
preflight → assess → map → extract-rules → brief (human gate) → uplift | transform | reimagine → harden
```

10 `/modernize-*` commands, 7 specialist agents, 6 deterministic multi-agent workflow scripts
(1,872 LOC). Each command is standalone — stop and review between any two — and
`/modernize-status` is read-only and reports what has run and what is next.

The three build commands are **three methods, not three tools**. `uplift` exists because the common
real case (a supported-version bump) is the one `transform` gets wrong by rewriting; if its delta
catalog shows most of the code is forced to change anyway, it says so and hands off to `transform`.

### 7. `platform-ui` — a read-only review surface (new component)

15,517 lines of new code: a .NET 10 minimal API (13 `GET` endpoints, read-only SQLite connections)
plus an Angular 21 web app over what v4 produces for a system — requirements with server-side
paging, FTS5 search and facets; merge candidates; citations resolved to the cited lines; topology,
domains, diagrams and generated docs.

**It reads a copy, never the live analysis tree.** `prepare_data.py` copies `knowledge.sqlite` and
emits sidecars into `platform-ui/data/`; the API has no other source. Two consequences: Layer 1 is
unreachable from the UI, so read-only is a property of the deployment and not just of the code; and
**whole client files never leave the analysis tree** — only the cited ranges, with eight lines of
context.

### 8. Licensing and provenance made explicit

`.claude/skills/code-modernization/` is Apache-2.0 © Anthropic, vendored. The pristine upstream
`LICENSE` ships unmodified (the copy §4(a) obliges us to give recipients); `LICENSE.md` carries
CapTech's terms; `NOTICE` carries attribution; `.claude-plugin/.upstream` records the upstream
commit this fork came from. Files CapTech modified carry a per-file modification line, and a CI test
fails if the duplicated licence copies drift.

## Measured facts

Every figure was measured in this repository; reference-corpus figures come from a real client
Java/JSP estate (the "NNG application") and are reproducible from the plans under
`docs/exec-plans/`, not from a clean checkout.

| The engine — `legacylift-search` | |
|---|---|
| Lines of Python | **16,017** across 45 modules (plus 10,009 comment lines) |
| Automated tests | **1,280 across 64 modules — full suite green, exit 0, 2026-09-15** |
| CLI commands | **30** — 16 index/search/graph/domain, plus 14 under `requirements` |
| SQLite tables | 24 across two stores — 9 disposable (Layer 0), 15 durable (Layer 1) |

| Against the reference corpus | |
|---|---|
| Source files discovered | **1,504** (up from 1,229 before the scope fix) |
| Symbols extracted | 16,268, every one with a content hash |
| Code-graph edges | 74,541, confidence-scored, unresolved edges kept |
| Searchable chunks | 15,398, tagged into 12 capability domains across 36 edges |
| Business rules mined in one run | **437** over four rounds, stored as 379 records |
| Offers collapsed onto a shared record | 106 → 48 (13.3%); all 48 groups read back and confirmed |
| Under-merged clusters | 34 — every internal pair queued as a merge candidate, 34 of 34 |
| Decision tables extracted | 39 (3–8 rules each, median 5) |
| Index coverage after four rounds | 3.07% — 473 of 15,398 chunks, the honest denominator |

**The test count matters more than the line count.** The engine is deterministic infrastructure an
LLM then reasons over, and determinism is only a claim until it is pinned: the suite runs against a
polyglot fixture repository with a hash-based embedder, entirely **offline**, so a regression in
chunking, graph resolution or requirement identity fails the build instead of surfacing in a client
deliverable. A `tests.yml` CI job now runs it on every PR to `main`, alongside `dotnet build` and
`ng build` for `platform-ui`.

**The notation was not invented.** Twenty survey threads through the requirements-engineering and
business-rule-extraction literature; **13 primary sources acquired and read directly** — ISO/IEC/IEEE
29148:2018, OMG SBVR v1.0 and KDM 1.4, Von Halle, Femmer et al. on requirements smells, the DeCoMi
prototype, a 24-study systematic review, and 10 arXiv preprints. EARS, Volere, Planguage, SOPHIST
MASTeR, Withall, SCR/Parnas, ReqIF and DMN were surveyed and **deliberately not adopted, each for a
recorded reason**. Every deviation from the standards is in a numbered register.

## Breaking changes and migration

| Change | What to do |
|---|---|
| **The v3 web application is deleted** (−36,211 lines). | Nothing replaces it for v3.7. v4's read surface is `platform-ui`, and it reads v4's store only. |
| **v3.7 skills are namespaced.** | Invoke `legacylift-classic:{skill}` — e.g. `/legacylift-classic:fact-graph`. Bare names resolved only before `v3.7.0`. |
| **v4 does not run v3.7 skills, read their output, or fall back to them.** | Decide which version an engagement uses before you start. `/modernize-preflight` checks whether v4's prerequisites are met. |
| **Generated output location differs by layout.** | In a `legacy/` + `analysis/` workspace it goes to `analysis/<system>/`; on a plain checkout it falls back to `<repo>/legacylift-docs/`. No `/modernize-*` command passes `--analysis-dir`. v3.7 always writes `{repository}/legacylift-docs/`. |
| **`knowledge.sqlite` lives beside the index, in the same directory.** | The Layer 0/1 boundary is logical, not physical: `index --reset` preserves Layer 1, but **clearing the analysis directory destroys domain tagging**. Re-run `tag-domains` before `map` if you have. |
| Client source is never written. | The source files themselves are read-only in every pathway; `legacylift-docs/index/` is gitignored. |

Before long runs — v3.7 documentation skills, or `assess` / `map` / `extract-rules` — set an
extended context window: `/model sonnet[1m]`.

## Known gaps, measured and on the record

None of these is a surprise waiting in a client engagement.

| Gap | Measurement | Consequence |
|---|---|---|
| Dense-vector coverage | ~70% of chunks never receive a dense vector, on both reference corpora | A cost filter never evaluated for recall. Written up as a call for a recall/precision evaluation, not a flag flip. |
| DTO catalog completeness | 187 of 437 rules were never shown to the data-object agent | One consumer field is 56.5% complete while looking finished. Must not ship as-is. |
| Dedupe key tiering | 34 clusters / 54 excess rows | Not a correctness defect — all 34 are queued for a reviewer — but the store is populated now, so changing the key is a migration. |
| Run-to-run variance | Two four-round runs, identical code and settings: 379 records / 117 files cited versus 656 / 140 | Large, and now a measured quantity. Any coverage claim has to be read beside it. |
| `platform-ui` tests | None yet | CI builds both halves, which catches a break but proves nothing about behaviour. Tracked in `docs/exec-plans/pending/platform-ui-tests.md`. |
| Cleartext credentials in `*.properties` | 15 files, including one production credential | Indexing them locally was a deliberate call; hosted embedding sends their contents off the machine regardless. Open design question, written up rather than left implicit. |
| Durable LOC counts | Computed at least three times per engagement, stored zero times | A one-column change, queued behind the shared migration mechanism. |

**There is no recall number, and that is deliberate.** There is no accepted ground truth for "the
business rules in this codebase," so no extraction tool can report recall. v4 reports **coverage
against the index** instead, and the measurable claim it hands a client is "a named human approved
this rule against these cited lines" — a stronger thing than a confidence score. Relatedly: the
extraction loop stops on a **round cap, not on saturation**, so corpus size is a budget decision and
437 rules is not "all the rules in this estate."

## What to take away

v4 moved LegacyLift from "an LLM reads your code and writes documents" to "a deterministic index and
a reviewed requirements store, with an LLM doing the judgement work in between." The difference a
client can see: citations that resolve, coverage stated as a number with its denominator, a re-run
that preserves their reviewers' work, and a recommendation between `uplift`, `transform` and
`reimagine` backed by a delta catalog rather than a preference.
