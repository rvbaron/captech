## Purpose / Big Picture

Today, LegacyLift can index a legacy repository (`legacylift-search index`) and search it semantically, but it has **no concept of a "capability domain"** — a business-meaningful grouping of code such as "Claims Management" or "Regulatory Filing." The only domain information anywhere comes from two weaker or transient sources: the v3 `fact-graph` skill derives domains bottom-up from namespace prefixes (producing many ungrouped bins), and the `modernize-assess` skill derives them top-down (grouped, with inter-domain dependency edges) but writes them only into a human-readable markdown table and a `ARCHITECTURE.mmd` diagram that no tool can query.

After this change, a user can associate **every file (and therefore every code chunk, symbol, extracted rule, and data-model fact) with exactly one capability domain**, and that association lives in a **durable SQLite database that survives re-indexing and can later be shipped to a shared or cloud store**. Concretely, after implementation a user can:

- Run `legacylift-search tag-domains --repo-root <repo> --domains domains.json` and have the assess-quality domains ingested into a durable `knowledge.sqlite`, with every source file assigned to a domain (or to a reserved `Unassigned` bucket).
- Run `legacylift-search search "eligibility validation" --repo-root <repo> --domain "Claims Management"` and get back only results whose code belongs to that domain.
- Run `legacylift-search domains --repo-root <repo>` and see the domain catalog with per-domain file and chunk counts.
- Run `legacylift-search render-architecture --repo-root <repo>` and get a `ARCHITECTURE.mmd` diagram generated deterministically from the SQLite domain catalog and its dependency edges — not hand-authored by an LLM.
- Re-index the repository (`legacylift-search index`) and observe that domain tags for unchanged and glob-matchable files stay correct with zero manual steps, while `legacylift-search validate` reports a distinct "domains" freshness line that goes loud when new, unclassified files appear.
- Hand-edit a single file's domain in the database and observe that the edit **survives** subsequent re-indexes (it is never clobbered by automatic re-tagging).

The observable end state is a durable, queryable, relational domain model that the code-search index and the ARCHITECTURE diagram both consume — the first step of a larger direction in which *all* downstream LegacyLift outputs are generated from SQLite rather than from ad-hoc files.

## Surprises & Discoveries

- Observation: `symbol_facts` (the M23–25 facts layer — annotations, SQL columns, type/signature facts) already exists but was built inside the **throwaway** `index.sqlite`, which `--reset` deletes.
  Evidence: `tools/legacylift_search/src/legacylift_search/store.py` defines `CREATE TABLE IF NOT EXISTS symbol_facts` at line ~346 inside `SQLiteStore.migrate` (the method is **public `migrate()`** at `store.py:173`, not `_migrate` — corrected per issue #32), and `Indexer.run` opens that store at `sqlite_path` under the gitignored index directory. Originally this motivated relocating `symbol_facts` into the durable store; on review (2026-07-17) that relocation was **dropped** — facts are re-derivable from source and every `--reset` re-embeds Chroma regardless (`indexer.py` unlinks `index.sqlite` and `rmtree`s the Chroma dir, ~lines 188–199), which is the dominant cost, so fact durability buys little. Meanwhile a cross-file store would break the two enforced foreign keys (`repo_files`, `symbols`) and the `IntegrityError`-based orphan-drop guard in `upsert_facts`. `symbol_facts` therefore stays in `index.sqlite`; only the authored domain tables go durable. See the 2026-07-17 revision in the Decision Log.

- Observation: `chromadb` 1.5.9 `collection.update(ids=[id], metadatas=[{"domain": ...}])` **merges** the supplied keys into each id's existing metadata rather than replacing the whole dict.
  Evidence: probe on 2026-07-17 — a record carrying the eight `upsert_chunks` metadata keys, updated with `{"domain": "core-services"}` alone, read back with all eight original keys intact **plus** `domain`. This confirms Milestone 4's stamp step (and the indexer's re-stamp) can pass only the `domain` key without a read-merge-write. The probe is preserved verbatim in **Artifacts and Notes** (re-run it if the chromadb pin moves off 1.5.9). Note: the probe also surfaced a benign Chroma Rust-backend teardown panic on process exit under Windows — teardown-only noise emitted after results are returned; unrelated to correctness. (Behavior is version-specific; it holds for the pinned 1.5.9 — see the chromadb version-pin note.)

- Observation (2026-07-20, implementation): the chromadb 1.5.9 `update`-MERGE behavior predicted by the probe held in practice — after `tag-domains`, a `src/` chunk's Chroma metadata read back as `domain=core-services` plus all eight original `upsert_chunks` keys intact. The Rust-backend teardown panic on Windows process exit is present but benign, exactly as noted.

- Observation (2026-07-20, implementation): a re-embed is required for the indexer to re-stamp a chunk's Chroma `domain`. Appending a trailing comment to a function leaves its chunk `text_sha256` unchanged, so the vector is skipped as already-present and never re-stamped — correct engine behavior. Consequence for operators: a `manual` edit to an *unchanged* file reaches the vector side only via a `tag-domains` reconcile, not by "touching" the file (which does not change the chunk hash). The M5 acceptance test was written to rewrite the function body so the chunk genuinely re-embeds.

- Observation (2026-07-20, implementation): the only real defect found in the final cross-milestone review was a `stats` "files tagged" figure that summed `unassigned + classified`, contradicting the plan's own M2 example (`… · 1 files tagged · 0 unassigned`, where "tagged" = classified) and `validate`'s coverage arithmetic. Fixed so "files tagged" counts classified files only; the test that had pinned the buggy value (`3 files tagged`) was corrected to `2`.


## Decision Log

The following decisions were finalized in the interview recorded in `domain-plan-notes.md` (2026-07-17, Darrell Norton with Claude). They are reproduced here so this plan is self-contained.

- Decision: SQLite is the source of record for domains (not a git-committed JSON file).
  Rationale: The strategic direction is to move *all* downstream outputs (business rules, data objects, domains) into a relational store so the whole knowledge base can eventually move to a shared/cloud database for team use. A JSON file would be a second artifact to reconcile.
  Date/Author: 2026-07-17 / Darrell Norton.

- Decision: The durable knowledge lives in a **separate database** (`knowledge.sqlite`) with its own lifecycle, not inside the code-search `index.sqlite`.
  Rationale: `index.sqlite` (chunks, vectors, graph) is deterministic, per-host, and deleted on `--reset`; domains and facts are expensive judgment/extraction that must persist. A separate DB matches the cloud-migration story: you ship the knowledge DB, the index is a local accelerator. **Superseded in part by the 2026-07-17 revision below: only the authored domain tables move into `knowledge.sqlite`; `symbol_facts` stays in `index.sqlite`.**
  Date/Author: 2026-07-17 / Darrell Norton.

- Decision: Domain assignments are stored at **file granularity**, single primary domain per file, keyed on `relative_path`.
  Rationale: `relative_path` is stable across content edits (no churn on reindex), matches assess's native output, and is one row per file. Chunk/symbol/fact domains are derived by join; a `domain` copy is denormalized into Chroma metadata only because Chroma cannot join at query time.
  Date/Author: 2026-07-17 / Darrell Norton.

- Decision: `modernize-assess` emits a **transient** `domains.json` (domain names, descriptions, path globs, inter-domain edges); a deterministic ingest step writes it into SQLite; the file is then disposable.
  Rationale: assess is an LLM skill that emits files, not database rows. The LLM authors compact glob rules (what it is good at); a deterministic resolver materializes exhaustive per-file assignments (what it is good at). Parsing assess's markdown was rejected as fragile. Nothing downstream reads `domains.json` after ingest; the cloud store ships `knowledge.sqlite` only.
  Date/Author: 2026-07-17 / Darrell Norton.

- Decision: Single primary domain per file in v1, with a reserved `Unassigned` catch-all; `file_domains` remains a table (not a column) so multi-domain is a non-breaking future extension.
  Rationale: A scalar `domain` gives a clean Chroma `where` filter and clean coverage math (partition sums to 100%). `Unassigned` guarantees all code rolls up and makes gaps loud. `Shared`/`Core` is a normal assess-authored domain, not a special case.
  Date/Author: 2026-07-17 / Darrell Norton.

- Decision: The tagging pass is a new deterministic `legacylift-search tag-domains` command (ingest + Chroma metadata stamp, idempotent); sequencing is `index → assess → tag-domains`. `modernize-assess` gets one minimal additive change plus the required CapTech attribution line.
  Rationale: assess consumes the index, so the index must exist first; tagging is a distinct third pass. Deterministic ingest belongs in the Python CLI alongside `index`/`search`.
  Date/Author: 2026-07-17 / Darrell Norton.

- Decision: 7-Auto freshness — on reindex the indexer self-resolves new/changed paths against the **stored** globs and stamps Chroma inline; `validate` gains a distinct domain-freshness axis.
  Rationale: The globs already live durably in the `domains` table; re-resolving a path is cheap and deterministic, so "add a file to an existing package" is zero-touch. Staleness narrows to genuinely new domains or re-groupings, which `validate` flags. Invariant: authored data (globs, edges, descriptions) is written only by ingest; derived data (`file_domains` glob rows, Chroma `domain` metadata) may be produced by either the indexer or `tag-domains`.
  Date/Author: 2026-07-17 / Darrell Norton.

- Decision: Minimal consumer scope. This feature makes domains available and switches the two consumers it owns — the ARCHITECTURE diagram and domain-scoped search — onto SQLite domains, plus a SQLite domain **query API**. Re-pointing the 13 documentation skills' "Phase 0" and building the fact-graph-compatible **bridge** are deferred to a gated follow-on.
  Rationale: Re-pointing the doc skills is the still-open "fact-graph Option A" decision; bundling it here would couple this feature to an unresolved architectural call. The bridge (a thin alias layer exposing fact-graph's helper names over SQLite) has no consumer in this scope, so building it now would be adapting to a contract we intend to retire (YAGNI). The query API it would wrap is built now because the owned consumers need it.
  Date/Author: 2026-07-17 / Darrell Norton.

- Decision: `ARCHITECTURE.mmd` becomes a **derived** artifact rendered deterministically from the SQLite `domains` + `domain_edges`; `modernize-assess` stops hand-authoring it and instead emits the nodes/edges as data in `domains.json`.
  Rationale: A derived diagram is always consistent with the stored tags and cannot drift from them.
  Date/Author: 2026-07-17 / Darrell Norton.

- Decision: `file_domains` carries provenance in v1 — `source` (`glob` | `manual`), `assess_run_id`, `confidence` — and enforces a `manual`-wins precedence rule (manual rows are never overwritten by glob resolution). Correction tooling/UX is deferred.
  Rationale: 7-Auto re-resolves paths against globs on every reindex and would otherwise silently clobber a human correction; the `source` column is what makes correction possible at all, so it cannot be a later addition. Confidence is effectively binary for glob matches (default 1.0) but the column is reserved for a future LLM/symbol-level classifier.
  Date/Author: 2026-07-17 / Darrell Norton.

- Decision: This work is a **new execplan** building on Milestones 22–25 of `semantic-code-search-graph-index.md`, not appended to it. M23–25 (the `symbol_facts` facts layer) is already shipped; under the 2026-07-17 revision this plan no longer relocates that table, so there is **no** coordination needed with the facts layer — `symbol_facts` stays exactly where M23–25 built it.
  Rationale: A durable knowledge store is a distinct architectural component with its own consumers and future-work roadmap; the index plan is already ~1,100 lines.
  Date/Author: 2026-07-17 / Darrell Norton.

- Decision (2026-07-17 revision, supersedes the relocation consequence of the separate-DB decision above): `symbol_facts` is **not** relocated; it stays in `index.sqlite`. Only the authored, non-re-derivable domain tables (`domains`, `domain_edges`, `file_domains`) live in the durable `knowledge.sqlite`.
  Rationale: (1) `symbol_facts` is re-derivable — every `index` run re-extracts it, and a `--reset` re-embeds all of Chroma (`indexer.py:199`), which dominates wall-clock, so preserving facts across a reset saves little. (2) Relocating it would break its two enforced foreign keys (`file_id → repo_files`, `subject_symbol_id → symbols`) — SQLite has no cross-file FKs — and with them the `IntegrityError`-based orphan-drop guard in `upsert_facts` (`store.py:657`) and the stability of its `file_id` rowid. (3) The genuinely non-re-derivable data is the `manual` `file_domains` corrections; those get durability from `knowledge.sqlite` regardless. Consequence: Milestone 1 no longer moves any table; the FKs and orphan guard are untouched. Moving `symbol_facts` to a shared store is deferred to the cloud-migration follow-on, where the FK-replacement work is done deliberately.
  Date/Author: 2026-07-17 / Darrell Norton (revision after implementation review).

- Decision (2026-07-17 revision, refines the 7-Auto freshness decision above): the reserved `unassigned` bucket is an **accepted gap, not staleness**. `unassigned` rows are written **only** by the explicit `tag-domains` pass (an assess-driven review event); the indexer's 7-Auto writes `glob` rows for matches and leaves non-matching new files **untagged** (no row). `validate` reports `domains: stale` iff untagged discovered files exist, `domains: fresh` when every discovered file has a row (regardless of how many are `unassigned`), and always shows `coverage%` and the `unassigned` count so a growing unassigned trend stays visible.
  Rationale: the original Milestone 7 conflated *untagged* (no row — tagging is behind the file set) with *unassigned* (a reviewed, legitimate no-domain gap). Counting unassigned as stale would make `validate` report `stale` forever on any real repo; not counting it left the milestone's own acceptance test (unmatched dirs → stale) impossible. Keying `stale` on untagged files, and making 7-Auto refuse to auto-manufacture `unassigned` rows, gives a crisp signal that goes loud exactly when new/unclassified code appears (matching the Purpose) and goes quiet as soon as an assess/`tag-domains` pass accounts for it. See issue 2 in `domain-enhancements-plan-issues.md`.
  Date/Author: 2026-07-17 / Darrell Norton (revision after implementation review).

- Relocate `symbol_facts` from `index.sqlite` into `knowledge.sqlite` — dropping its two SQL foreign keys for application-level cascades, and replacing the FK-based orphan-drop guard in `upsert_facts` with an in-process persisted-symbol-id membership check. ## Context and Orientation

This section assumes no prior knowledge of the repository. Read it before touching code.

**Where the tool lives.** The code-search tool is a self-contained Python package at `tools/legacylift_search`. Its importable modules are under `tools/legacylift_search/src/legacylift_search/`. Tests are under `tools/legacylift_search/tests/`. The command-line entry point is the `legacylift-search` script, which maps to `legacylift_search.cli:app` (a Typer application). During development you can run it as `py -3.12 -m legacylift_search.cli <command>` from inside `tools/legacylift_search` (Python 3.12 is the supported interpreter on this Windows host; 3.13 also works, 3.14 does not — dependency wheels are missing).

**The existing CLI verbs** (defined in `src/legacylift_search/cli.py`, each decorated with `@app.command(...)`): `init-config`, `index`, `backfill-vectors`, `validate`, `search`, `symbols`, `callers`, `callees`, `facts`, `stats`, `coverage`, `dump-ast`. This plan adds three new verbs: `tag-domains`, `domains`, and `render-architecture`, and extends `search`, `validate`, and `stats`.

**The two databases (after this plan).** Today there is one SQLite file. This plan introduces a second:

- The **code-search index** at `<repo-root>/legacylift-docs/index/code-search/` contains `index.sqlite` (chunks, an FTS5 full-text table, the symbol/reference/graph tables, and a `vectors_present` cache) plus a Chroma vector store directory. This directory is **gitignored** (see the root `.gitignore` rule `repos/*/legacylift-docs/index/`) and is **deleted and rebuilt** when `index` is run with `--reset`. The path is computed by `resolve_index_dir(repo_root, manifest)` in `src/legacylift_search/config.py`, which returns `repo_root / manifest.index.index_dir` (default `legacylift-docs/index/code-search`).
- The **durable knowledge store** (new) at `<repo-root>/legacylift-docs/knowledge/knowledge.sqlite` contains the new domain tables (`domains`, `domain_edges`, `file_domains`). `symbol_facts` is **not** moved here — it stays in `index.sqlite` (see the 2026-07-17 Decision Log revision). This directory is **outside** the gitignored index path and is **never touched by `--reset`**. A local binary SQLite file should not be committed to git. Because this directory sits **outside** the already-ignored `index/` path, it is not covered by any existing rule, so add explicit `.gitignore` rules for the file and its WAL/SHM siblings — `repos/*/legacylift-docs/knowledge/knowledge.sqlite*` and the `repos/*/*/…` variant (see Milestone 1). "Durable" here means "survives `--reset` and lives on disk for export," not "committed to git." The `knowledge/` **directory itself is not committed** (git cannot track an empty directory, and its only content is the gitignored DB, issue #18); it is created on demand at runtime by `KnowledgeStore.__init__` (which `mkdir(parents=True, exist_ok=True)`s its parent), so no `.gitkeep` placeholder is needed. Its path is computed by a new `resolve_knowledge_dir(repo_root, manifest)` helper analogous to `resolve_index_dir`.

**Key existing classes and functions you will touch or mirror:**

- `SQLiteStore` in `src/legacylift_search/store.py` — constructed as `SQLiteStore(sqlite_path: Path)`; its **public `migrate()`** method (`store.py:173`) creates all tables idempotently with `CREATE TABLE IF NOT EXISTS` **and** sets the connection pragmas `PRAGMA journal_mode=WAL` / `PRAGMA foreign_keys=ON` (`store.py:180-181`). Important for Milestone 1: the pragmas are in `migrate()`, **not** in `__init__` — `SQLiteStore.__init__` (`store.py:157-164`) only stores `self.sqlite_path` and sets `self.conn = None`, deferring to a lazy `_connect()`; and `migrate()` is **not** auto-run on construction — callers invoke it explicitly (e.g. `indexer.py:960`). `SQLiteStore` currently owns `symbol_facts` and its `upsert_facts`, `facts`-query, and `clear_reindex_artifacts` logic. (Corrected per issue #32; the earlier "`_migrate` / pragma-in-`__init__`" citations were wrong.)
- `ChromaVectorStore` in `src/legacylift_search/vector_store.py` — `upsert_chunks(chunks, embeddings)` builds a per-chunk metadata dict (currently keys `relative_path`, `language`, `chunk_kind`, `symbol_id`, `symbol_path`, `start_line`, `end_line`, `text_sha256`) and calls `collection.upsert(...)`. `query(query_embedding, limit)` currently passes **no** `where` filter to `collection.query(...)`.
- `SearchEngine` in `src/legacylift_search/search.py` — `search(query, limit)` fuses vector ranks (`_vector_ranks` → `vector_store.query`) and lexical ranks (`_lexical_ranks` → `store.search_lexical`) with reciprocal-rank fusion.
- `Indexer` in `src/legacylift_search/indexer.py` — `Indexer(manifest, repo_root)`; `run(...)` is the 15-step pipeline that opens `SQLiteStore(sqlite_path)` and `ChromaVectorStore(...)`, discovers files, extracts in a process pool, writes SQLite, builds the graph, and embeds/upserts to Chroma.
- `Manifest` / `IndexConfig` in `src/legacylift_search/config.py` — Pydantic v2 models loaded from `<repo-root>/semantic-search.manifest.json`.
- `SymbolFact` in `src/legacylift_search/models.py` — the fact row model, fields `id`, `subject_symbol_id`, `predicate`, `object`, `attributes`, `evidence`, `confidence`, `relative_path`, `start_line`, `language`.

**Terms defined in plain language:**

- *Capability domain* (or just *domain*): a business-meaningful grouping of source files, such as "Claims Management." Produced top-down by the `modernize-assess` skill, which clusters subsystems into roughly 5–12 domains and identifies how they depend on each other.
- *Back-annotate*: to attach a domain label to code that was indexed *before* the domains were known. The index is built first (assess needs it), so domains are added in a later pass.
- *Glob*: a path pattern such as `src/Claims/**` that matches many files. assess authors globs; the ingest step resolves them against the real file list.
- *`modernize-assess`*: a Claude Code skill defined at `.claude/skills/code-modernization/commands/modernize-assess.md`. It runs subagents to produce a modernization assessment, including the domain table and a Mermaid dependency diagram written to `analysis/<system>/ARCHITECTURE.mmd`. This skill is Apache-2.0 licensed by Anthropic; per `CLAUDE.md`, any edit to a file under `.claude/skills/code-modernization/` must carry a CapTech attribution line (see Milestone 3).
- *Chroma*: the vector database storing one embedding per code chunk, with a small metadata dict per chunk. It supports filtered similarity queries via a `where={"key": "value"}` argument.
- *`--reset`*: a flag on `legacylift-search index` that deletes and rebuilds the code-search index from scratch.


## Plan of Work

The work proceeds in eight milestones, each independently verifiable. The dependency order is: Milestone 1 (knowledge DB) underpins everything; Milestone 2 (schema + query API) is consumed by Milestones 4, 6, 7, and 8; Milestone 3 (assess emission) produces the input to Milestone 4 (ingest); Milestone 5 (7-Auto) builds on Milestone 4's resolver; Milestones 6–8 are the owned consumers.

Throughout, hold the **authored-vs-derived invariant**: the *authored* domain data (domain names, descriptions, path globs, inter-domain edges) is written **only** by the Milestone 4 ingest step reading `domains.json`. The *derived* data (per-file `glob` assignments, Chroma `domain` metadata) may be produced by either `tag-domains` or the indexer, because it is a deterministic function of the authored globs and the file list. Human `manual` rows are authored-by-hand and always win. A companion invariant governs the vector index: a chunk's Chroma `domain` metadata is a **derived mirror of the authoritative `file_domains` row** for its file — for **every** row value, `glob` / `manual` / the reserved `unassigned` (issue #44). Both stampers (`tag-domains` and the indexer) copy the row's `domain` into Chroma and never compute a Chroma domain that disagrees with the row; the only time no `domain` key is written is when the file has **no** row at all (untagged). This is what lets a human `manual` correction reach vector-scoped search, and keeps `search --domain "Unassigned"` consistent across the vector and lexical sides even after a file is re-embedded.

All milestone validation uses the bundled `tests/fixtures/polyglot_repo` fixture, not the large `repos/ctcm/ctcm-api` repository. Prior milestones in the index plan established that at-scale ctcm runs exceed the harness's ~10-minute background-command wall-clock cap; the fixture exercises every code path deterministically and quickly. At-scale ctcm validation is a manual, unconstrained-host follow-up noted where relevant.

### Milestone 2 — Domain schema, query API, `domains` command, per-domain stats

Goal: define the durable domain tables and the read API over them, with a listing command and count statistics — provable against hand-inserted rows before any assess integration exists.

At the end of this milestone `KnowledgeStore` owns three tables and a set of query methods; `legacylift-search domains --repo-root <repo>` lists the catalog with per-domain file and chunk counts; and `stats` gains a domain summary.

Schema (create in `KnowledgeStore.migrate`, all `CREATE TABLE IF NOT EXISTS`):

    domains(
      domain_id     TEXT PRIMARY KEY,   -- stable slug, e.g. "claims-management"
      name          TEXT NOT NULL,      -- display name, e.g. "Claims Management"
      description   TEXT,
      path_globs    TEXT NOT NULL,      -- JSON array of glob strings, authored by assess
      assess_run_id TEXT,               -- provenance: which assess run produced this
      display_order INTEGER NOT NULL DEFAULT 0
    )

    domain_edges(
      from_domain TEXT NOT NULL,
      to_domain   TEXT NOT NULL,
      kind        TEXT NOT NULL DEFAULT '',  -- e.g. "calls", "shares-data"; never NULL — a NULL
                                              -- PK column lets duplicate edges slip past INSERT OR REPLACE
      evidence    TEXT,
      PRIMARY KEY (from_domain, to_domain, kind)
    )

    file_domains(
      relative_path TEXT PRIMARY KEY,   -- one primary domain per file
      domain        TEXT NOT NULL,      -- domain_id, or the reserved "unassigned"
      source        TEXT NOT NULL CHECK (source IN ('glob','manual')),
                                        -- HOW the row was produced, a strict two-value enum:
                                        --   'glob'   = written by the glob resolver (tag-domains
                                        --              OR the indexer's 7-Auto). This is the source
                                        --              even for an unmatched file, whose row carries
                                        --              domain='unassigned' — "unassigned" is a
                                        --              domain VALUE, never a source value (issue #43).
                                        --   'manual' = hand-authored human override; never overwritten
                                        --              by glob resolution (manual-wins).
      assess_run_id TEXT,
      confidence    REAL NOT NULL DEFAULT 1.0
    )

Reserve the sentinel `domain_id = "unassigned"` (display name "Unassigned"). **It is a reserved `file_domains.domain` *value*, not a `domains`-table row (issues #28, #30):** the resolver/ingest writes `file_domains` rows carrying `domain = "unassigned"`, but never inserts a `domains` row for it. The `domains`/`stats` commands synthesize the "Unassigned" display line from the `file_domains` count. Keeping it out of the `domains` table means `list_domains()` never returns it, so it can never leak into glob precedence (Milestone 4/5), into the `ORDER BY display_order` ordering, or into `render-architecture`'s node set (Milestone 8) — all three are unaffected by construction, and the "final `unassigned` line" in the `domains` command is a synthesized trailer, not an ordered row. (Name resolution for `search --domain "Unassigned"` therefore special-cases the reserved slug — see Milestone 6.) Index `file_domains(domain)` for fast per-domain lookups.

Query API on `KnowledgeStore`: `list_domains() -> list[DomainRecord]`; `get_domain_edges() -> list[DomainEdgeRecord]`; `files_for_domain(domain_id) -> list[str]`; `domain_for_file(relative_path) -> str | None`; `domain_file_counts() -> dict[str, int]`. (Architecture rendering is **not** added here — it is deferred to Milestone 8.) Define `DomainRecord`/`DomainEdgeRecord` Pydantic models in `models.py`.

**`list_domains()` ordering is load-bearing (issue #14).** It **must** return rows ordered by `display_order` (then `domain_id` as a stable tiebreaker) — `ORDER BY display_order, domain_id`. Glob precedence is "first matching domain in declaration order wins" (Milestone 4), and the indexer's 7-Auto (Milestone 5) drives that precedence off `list_domains()` while `tag-domains` drives it off the `domains.json` array order. Because ingest assigns `display_order = array index`, ordering `list_domains()` by `display_order` is exactly what makes the two stampers resolve an ambiguous (multi-domain-matching) file to the **same** domain. Without this guarantee (e.g. if rows came back in PK or physical order) reindex could silently disagree with `tag-domains`. `render-architecture`'s node sort (Milestone 8) uses the same ordering.

CLI: add `@app.command("domains")` in `cli.py` that opens the knowledge DB and prints each domain with its file count and its chunk count, plus a final `unassigned` line. The chunk count needs both databases — `file_domains` lives in `knowledge.sqlite`, `chunks` in `index.sqlite` — which are **separate files, so a single-statement SQL join is impossible**. **Prefer reading the two tables over separate connections and joining in Python (issue #34).** (Close both the raw `sqlite3` connection to `index.sqlite` and the `KnowledgeStore` when done — on Windows an un-closed connection leaves `-wal`/`-shm` handles dangling; issue #52.) The tempting alternative — `ATTACH DATABASE 'file:<index.sqlite>?mode=ro' AS idx` on the knowledge connection — is **unreliable on a WAL database**: SQLite cannot open a WAL database *read-only* while a live `-wal`/`-shm` exists (a read-only connection can't create/attach the shared-memory index), and a normal `index` run frequently leaves the WAL un-checkpointed, so the read-only ATTACH intermittently fails with "unable to open database file." If you attach at all, attach `index.sqlite` **read-write** (plain `ATTACH DATABASE '<index.sqlite>' AS idx`, no `mode=ro`) so SQLite can manage the `-shm`, and simply never write through it; but the Python two-connection join sidesteps the hazard entirely and is the recommended path. The **knowledge** side just uses the normal `KnowledgeStore` constructor — which opens WAL read-write and creates the dir, and has no read-only mode (issue #25) — but see the existence-probe caveat below. **Degrade gracefully when a sibling DB is absent (issues #19, #33):** if `index.sqlite` does not exist (repo never indexed), report chunk counts as `0`/`n/a` rather than letting the join throw; if `knowledge.sqlite` does not exist (test with `Path.exists()` **before** constructing `KnowledgeStore`, since construction would create it — issue #33) or it has no `domains` rows, `domains`/`stats` print a "no domains — run `tag-domains`" line instead of an unhandled exception. Extend `stats` to append a one-line domain summary (`N domains · M files tagged · K unassigned`), or `no domains yet` when the knowledge DB is empty/absent. **Both `domains` and `stats` must intersect their file counts with the discovered file set (call `discover_source_files` and drop `file_domains` rows for undiscovered paths) — the same #42/#55 guard `validate` uses — so a ghost row surviving a `--reset` (see Milestone 5, issue #55) can never make these commands over-count while `validate` reports correctly. This is stated in Interfaces and Milestone 5; it is repeated here because it is a requirement *of this command*, not only of `validate`, even though the ghost scenario only becomes reachable once Milestones 4–5 land.**

Acceptance: with no assess run, manually insert two domain rows and a few `file_domains` rows via a short Python snippet (shown in Concrete Steps), then `legacylift-search domains` lists them with correct counts, and `stats` shows the domain summary. This proves the schema and read path independently of assess.

### Milestone 4 — `tag-domains` command: ingest, resolve, stamp

Goal: turn a `domains.json` into durable per-file domain rows and Chroma metadata, deterministically and idempotently.

At the end of this milestone, `legacylift-search tag-domains --repo-root <repo> --domains <path>` (1) parses and schema-validates `domains.json`, (2) writes the `domains` and `domain_edges` tables, (3) resolves each domain's globs against the discovered file set and writes `file_domains` rows with `source='glob'`, sending unmatched files to `unassigned`, and (4) updates each affected chunk's Chroma metadata with a `domain` key via `collection.update(...)` — with **no re-embedding**.

Work: add `@app.command("tag-domains")` in `cli.py`. Implement the logic in a new `src/legacylift_search/domain_tagger.py` with a `DomainTagger` class so the same resolver can be reused by the indexer in Milestone 5. Key functions:

- `load_domains_json(path) -> DomainsFile` (a Pydantic model with `schema_version`, `assess_run_id`, `domains`, `edges`) — this doubles as the Milestone 3 validator.
- `resolve_file_domains(files: list[str], domains: list[DomainRecord]) -> dict[str, tuple[str, float]]` — for each file, return `(domain_id, confidence)`. Match globs with `pathspec` using its `gitwildmatch` syntax (already a dependency — the discovery layer uses `pathspec` for gitignore-style matching); do **not** use `fnmatch`, whose `*`/`**` and path-separator semantics differ and would make resolution non-deterministic relative to how assess authors globs. **Precedence is the order of the `domains` argument** — the resolver walks `domains` as given and the first domain whose glob set matches wins; if a later domain also matches, log a warning naming the file and both domains (ambiguity is a data-quality signal). Both callers must pass `domains` in `display_order` for this to be deterministic (issue #14): `tag-domains` passes the `domains.json` array order (which ingest also stores as `display_order = array index`), and the indexer passes `list_domains()`, which is `display_order`-sorted. The resolver does not re-sort — it trusts caller order — so the `display_order` guarantee lives in `list_domains()`. Files matching no domain map to `("unassigned", 1.0)`. `tag-domains` persists these as explicit rows with **`domain='unassigned'`, `source='glob'`** (issue #43 — `unassigned` is a domain *value*; the row is still glob-*sourced* because the glob resolver produced it) — an accepted-gap review event — whereas the indexer's 7-Auto (Milestone 5) leaves non-matching files untagged instead; Milestone 7 explains why this distinction drives the freshness verb.
- The stamp step: for **every** file in `file_domains` — `glob` and `manual` rows alike — look up its chunk ids from `index.sqlite` (`SELECT id FROM chunks WHERE relative_path = ?`) and stamp Chroma with *that row's* `domain` via a new thin `ChromaVectorStore.update_domain_metadata(chunk_ids: list[str], domain: str)` helper (encapsulating the `collection.update(...)` call so the indexer reuses it). Chroma's `update` **merges** metadata — verified empirically against the pinned chromadb 1.5.9 (see Surprises & Discoveries) — so passing only the `domain` key preserves the chunk's other seven metadata keys; no read-merge-write is needed. Because it stamps from the authoritative row, re-running `tag-domains` **reconciles Chroma to any `manual` corrections** made since the last run, with no re-embedding — this is the supported way to make a hand-edited domain take effect on the vector side of search.
  - **Not every SQLite chunk id is a Chroma vector (issue #15).** `chunks` (and FTS5) hold *all* chunks, but the embed phase skips below-threshold chunks when `chunking.embed_min_tokens > 0` (`config.py` — those chunks keep full lexical/symbol recall but carry no dense vector), so `SELECT id FROM chunks` can return ids that were never upserted into Chroma. Calling `collection.update(...)` on an id absent from the collection can raise/warn depending on chromadb version. `update_domain_metadata` must therefore be robust to missing ids — either restrict the id set to chunks known to be embedded (join against the `vectors_present` cache) or wrap the `collection.update(...)` call defensively (the sibling `delete_chunks` already does the latter, `vector_store.py:143-147`). Prefer the `vectors_present` restriction: it avoids per-call exception cost and is exact. The default fixture runs with `embed_min_tokens=0` (everything embedded), so this path is exercised only at scale — call it out here so it isn't discovered on the first real ctcm run.

Idempotence: `tag-domains` uses `INSERT OR REPLACE` for `domains`/`domain_edges` and upserts `file_domains` **except** it must never overwrite a `source='manual'` row (the manual-wins rule, enforced here and in Milestone 5). Re-running the command produces the same state.

Reap stale **authored** rows (issue #41): the authored tables (`domains`, `domain_edges`) are written with `INSERT OR REPLACE`, which only touches rows named in the incoming `domains.json`. A domain (or edge) that an *earlier* assess run authored but the *current* `domains.json` no longer contains — merged, renamed, or re-scoped away — would otherwise linger forever and leak into glob precedence (its stored globs still match files, and its low `display_order` can outrank current domains), into `render-architecture` as a phantom node (the issue-#36 edge guard does not catch it — it is a node, not a dangling edge), and into the M8 byte-identical guarantee (the SQLite source would carry the orphan the fresh `--domains` source does not). So after the `INSERT OR REPLACE`, **reconcile the authored tables to the ingested set**: `DELETE FROM domains WHERE domain_id NOT IN (<ingested ids>)` and `DELETE FROM domain_edges WHERE (from_domain,to_domain,kind) NOT IN (<ingested edge keys>)`. Unlike `file_domains`, these tables carry **no** hand-authored `manual` rows to protect, so a wholesale "delete-not-in-input" reap is safe. **Warn on removal:** when the reap drops one or more domains, print an explicit notice naming them and the count of files each reclassified off (e.g. `dropped 1 domain no longer in domains.json: legacy-billing (7 file(s) reclassified)`), mirroring the manual-override notice, so an operator always sees a domain vanish rather than discovering it silently. The dropped-domain names and count are carried on `TagStats`.

Reap stale **`file_domains`** rows (issues #38, #42): after resolving, delete any `file_domains` row whose `relative_path` is no longer in the discovered set — a file removed from the repo — **regardless of `source`, including `manual`**. This is a deliberate reversal of the original #38 rule ("never delete a `manual` row"), settled 2026-07-17: the `manual` tag exists for exactly one purpose — to stop 7-Auto glob re-resolution from overwriting a **live** human decision — and a deleted file has no live decision to protect. The manual-wins rule is therefore unchanged for files that still exist (glob resolution never overwrites a live `manual` row); it simply no longer means the row is immortal. Keeping `manual` rows for deleted files bought nothing and cost real bugs: it inflated `classified`/`coverage` (`validate` could report `stale · coverage 200%` — issue #42) and drifted the per-domain **file** counts (read from `file_domains`) above the discovered set. The sole tradeoff accepted: if a file at the identical path is deleted and later re-added (e.g. a branch switch), its manual override is not auto-restored — 7-Auto reclassifies it by glob and the operator re-applies the override. Because the reap now removes *every* undiscovered row, after a `tag-domains` run `file_domains ⊆ discovered` holds, which is what lets Milestone 7's counts be correct (see issue #42 there).

**Reconcile order (issues #38, #41).** The two reaps and the resolve run in one command in this order: (1) `INSERT OR REPLACE` the authored tables from `domains.json`; (2) reap authored `domains`/`domain_edges` rows absent from the ingest (#41); (3) resolve every discovered file against the **surviving** globs and write `file_domains` (a file previously in a now-dropped domain is reclassified here — to another domain or `unassigned`), honoring manual-wins for live files; (4) reap `file_domains` rows for **any** undiscovered path regardless of `source`, including `manual` (#38, #42). This keeps `tag-domains` the single reconcile point for every durable row, authored and derived.

Missing index (issue #39): the stamp step reads chunk ids from `index.sqlite`. If `index.sqlite` does not exist (the repo was never indexed, i.e. `tag-domains` was run out of the `index → assess → tag-domains` order), fail with a clear, actionable error ("no code-search index found at `<path>` — run `legacylift-search index` first") rather than throwing on the first chunk-id lookup.

Manual-override visibility: whenever `source='manual'` rows are present, `tag-domains` prints an explicit notice counting them and naming the paths (e.g. `preserved 3 manual domain override(s) — not overwritten by glob resolution: src/foo.py, src/bar.py, …`), so an operator is always aware that hand-set overrides exist and were honored rather than silently skipped. The count is carried on the returned `TagStats`.

Discovered file set: reuse the existing discovery function the indexer uses (`discover_source_files` in the discovery module) so `tag-domains` classifies exactly the files that were indexed. Note `discover_source_files` returns `list[SourceFile]`, not `list[str]` (issue #17) — `resolve_file_domains` takes `list[str]`, so the caller passes `[sf.relative_path for sf in discover_source_files(repo_root, manifest)]` (`SourceFile.relative_path` exists in `models.py`). A one-line adapter, but name it so it isn't missed.

Acceptance (fixture): the `tests/fixtures/polyglot_repo` tree has natural sub-directories (`src/`, `annotations/`, `hierarchy/`, `database/`). Author a fixture `domains.json` mapping, e.g., `src/**`→"Core Services", `database/**`→"Data Layer", with `annotations/**` and `hierarchy/**` deliberately left unmatched. After `index` then `tag-domains`: `file_domains` has `glob` rows for `src` and `database` files, `unassigned` rows for the rest; `domains` lists two domains plus `unassigned`; the Chroma metadata for a `src` chunk contains `domain="core-services"` (verify by reading one record back). A second `tag-domains` run leaves the DB **logically identical** — same rows, no row-level diff (assert on row content, not raw bytes: a WAL-mode SQLite file can differ byte-wise between runs even with identical content — issue #24).


### Milestone 5 — Indexer 7-Auto self-resolution and manual-wins precedence

Goal: keep domain tags fresh across re-indexing without a manual `tag-domains` step, using the globs already stored in the knowledge DB, while guaranteeing human corrections survive.

At the end of this milestone, running `index` (cold or incremental) will, for every changed or new file, resolve its domain against the **stored** globs (via the shared `DomainTagger.resolve_file_domains`), write/refresh a `source='glob'` `file_domains` row **only for files that match a domain glob** (leaving non-matching new files untagged — see Work), and stamp its chunks' Chroma metadata inline during the embed/upsert phase. For any file whose `file_domains` row has `source='manual'` it must **never overwrite that row's domain**; when it (re)embeds such a file's chunks it stamps them with the *manual* row's domain (never a recomputed glob value), so the vector index mirrors the human's decision instead of reverting to the glob answer. (A `manual` edit made directly to an *unchanged* file's row is propagated to Chroma by a `tag-domains` reconcile — see Milestone 4 — because the indexer only re-stamps files it re-embeds.) If the knowledge DB has no `domains` yet (never tagged), the indexer does nothing domain-related (no globs to resolve against), and files remain untagged until the first `tag-domains` run.

Work: in `indexer.py`, after the SQLite write phase and before/at the Chroma upsert, open the knowledge DB, load the stored domains, and for the batch of changed/new files compute `resolve_file_domains`, honoring manual-wins by first reading existing `file_domains.source` for those paths. Persist a `file_domains` row only for files that **match a domain glob** (`source='glob'`); files matching no glob are left **untagged** — the indexer never manufactures `unassigned` rows (those come only from the explicit `tag-domains` pass), so a genuinely new/unclassified file surfaces as `stale` in `validate` (Milestone 7) rather than being silently swept into `unassigned`. On any reindex where the knowledge DB holds `source='manual'` rows, the indexer emits the same manual-override notice `tag-domains` does — counting the **total** manual rows in the DB (via `SELECT COUNT(*) FROM file_domains WHERE source='manual'`), not only those in the changed batch — so awareness that overrides exist is standing, even on a routine incremental run that touches none of the overridden files. For each file being (re)upserted, the `domain` written into Chroma is the **authoritative** value for that file, computed by a single uniform rule (issue #44): **if a `file_domains` row already exists for the file, mirror that row's `domain` verbatim** — whether it is `manual`, a glob-matched domain, *or* the reserved `unassigned` (written earlier by `tag-domains`); **else** use the freshly glob-resolved domain if the file matches one (a new file — also write its `glob` row); **else** omit the key (a new file matching nothing — it stays untagged, driving the Milestone 7 freshness signal). This subsumes manual-wins on the vector side (an existing `manual` row is mirrored, never recomputed) and closes the gap where a re-embedded `unassigned` file would otherwise lose its `domain="unassigned"` Chroma key on the full-record `upsert` and silently drop out of `search --domain "Unassigned"` (issue #44). Mirroring an existing `unassigned` row is **not** the indexer "manufacturing" an `unassigned` row — the row already exists (only `tag-domains` creates them); the indexer merely keeps Chroma faithful to it. Pass it via a new optional `domain_by_chunk: dict[str, str]` argument on `ChromaVectorStore.upsert_chunks`, merged into the per-chunk metadata dict (default absent → omit the key, matching today's behavior). For unchanged files under the incremental fast-path, their existing Chroma metadata already carries the correct domain, so nothing is needed — with one exception: a `manual` domain hand-edited onto an unchanged file's row reaches Chroma only via a `tag-domains` reconcile, since that file is not re-embedded.

**The Chroma upsert is a single shared helper with two callers (issue #22).** `vector_store.upsert_chunks(...)` is called in exactly one place — `Indexer._embed_and_upsert` (`indexer.py:868`, inside the method defined at `indexer.py:776`) — and that helper is invoked from **both** `run()` (`indexer.py:705`) and `backfill_vectors()` (`indexer.py:1009`). So "stamp inline during the embed/upsert phase" means threading the domain map through `_embed_and_upsert`: extend its signature to accept `domain_by_chunk: dict[str, str] | None` and forward it to `upsert_chunks`; `run()` computes the map (from the resolved `file_domains`/manual rows for the batch) and passes it, and `backfill_vectors()` must **also** open the knowledge store and pass the map. This matters because `backfill_vectors()` is the resume path for an interrupted `--reset` (`indexer.py:914-920`): on a cold reset every chunk is missing, so a reset **completed via `backfill-vectors` re-creates all vectors through this helper**, and today `backfill_vectors()` opens only `SQLiteStore` (`indexer.py:959`), never the knowledge store. If it does not stamp, the rebuilt Chroma vectors carry no `domain` metadata even though the surviving `knowledge.sqlite` still has the tags, and `--domain` vector search (Milestone 6) silently returns nothing until a `tag-domains` reconcile. Have `backfill_vectors()` open the knowledge store and pass the domain map through `_embed_and_upsert` for parity with `run()`; the Recovery section additionally documents the `tag-domains` reconcile as the operator-facing fallback. Note the text-dedup fan-out (`indexer.py:859-866`): the domain map must be keyed by `chunk.id` and cover every fanned member, not only the representative chunk — correct by construction, since domain is per-file and each fanned member carries its own `relative_path`.

**Reap `file_domains` for deleted files on reindex (issue #45).** The incremental pipeline already computes `deleted_paths` — files present in `repo_files` but no longer on disk — and drops their `index.sqlite` artifacts via `delete_file_artifacts` (`indexer.py:265-272`). That cleanup touches only `index.sqlite`; it has no knowledge of `knowledge.sqlite`, so without action here a deleted (or renamed — a rename is a new path plus a deleted old path) file's `file_domains` row would survive in the knowledge DB until the next `tag-domains` run, drifting the per-domain file counts and (absent Milestone 7's defensive intersect) `coverage`. So when `deleted_paths` is non-empty, the indexer must `DELETE FROM file_domains WHERE relative_path = ?` for each — **regardless of `source`, including `manual`** (same source-agnostic rule as the `tag-domains` reap, issues #38/#42: a deleted file has no live decision to protect). This makes the indexer a second reconcile point for row deletion (it still is **not** one for authored `domains`/`domain_edges`, which only `tag-domains` writes and reaps). Guard it so it is a no-op when the knowledge DB has no `domains` yet (never tagged) — consistent with "the indexer does nothing domain-related" in that state.

**Key `file_domains` reaping to the discovered set, not to `deleted_paths`, so `--reset` reconciles too (issue #55).** `deleted_paths` is computed as `existing_shas.keys() − current_paths` (`indexer.py:266`), and on a `--reset` run `existing_shas` is **empty** — the DB was wiped, "so every file is processed from scratch" (`indexer.py:259-268`). So a reap keyed on `deleted_paths` **never fires on `--reset`**: a file that was tagged, then deleted from disk, then `index --reset`-ed (with no intervening `tag-domains`) keeps its ghost `file_domains` row, and the plan's `file_domains ⊆ discovered` invariant does **not** hold after a reset. This is not merely cosmetic — it makes the `domains`/`stats` commands (which read raw `domain_file_counts()`, M2) over-count that domain's files while `validate` (which intersects with the discovered set, #42) reports correctly, so the two commands **contradict each other** on the same repo state. Fix both facets: (1) the indexer reaps `file_domains WHERE relative_path NOT IN <discovered current_paths>` — a superset of the `deleted_paths` reap that also catches reset-window ghosts and any externally-inserted stray row — still `manual`-inclusive and still guarded on "knowledge DB has domains"; and (2) apply the same discovered-set intersect the #42 guard gives `validate` to `domain_file_counts()` (and thus the `domains`/`stats` output), so a read command can never disagree with `validate` in the window before a reconcile. `discover_source_files` is already computed in `run()` (`indexer.py:247`), so the reap set is free.

Acceptance (fixture): (a) after Milestone 4's tag, add a new file under `src/` and run incremental `index`; the new file gets a `glob` `file_domains` row and its chunk carries `domain` metadata, with no `tag-domains` call. (b) Manually update one `src` file's `file_domains` row to `source='manual', domain='data-layer'`; touch that file and re-index. Confirm (i) the row still reads `manual`/`data-layer` (7-Auto did not overwrite it), and (ii) that file's chunk Chroma metadata now reads `domain='data-layer'` — the manual decision reached the vector index, it was not left at `core-services`. Then, separately, edit a *different* `src` file's row to `manual` **without touching the file** and run `tag-domains` (no reindex); confirm its Chroma metadata also flips to the manual domain (the reconcile path). (c) Run `index --reset`; confirm the knowledge DB (and thus domains + manual rows) survive, and existing `glob` rows persist — mirrored verbatim into Chroma from the surviving `file_domains` rows per the issue-#44 uniform rule, **not** recomputed (issue #53) — while any brand-new file matching a glob gets a fresh `glob` row.


### Milestone 6 — `--domain` filter on `search`

Goal: let a user restrict semantic search to a single domain.

At the end of this milestone, `legacylift-search search "<query>" --repo-root <repo> --domain "<name-or-id>"` returns only results whose file belongs to that domain. The vector side uses Chroma's native `where` filter on the denormalized `domain` metadata; the lexical side is post-filtered against the set of files in the domain (FTS5 lives in `index.sqlite` and cannot join the knowledge DB directly, so post-filtering by `relative_path` membership is the clean approach).

Work: add a `--domain` option to the `search` command in `cli.py`, resolving a display name **or** a `domain_id` to a `domain_id` via the knowledge DB. **`--domain` is the only search path that touches the knowledge DB, and it is a read-only consumer, so probe `knowledge.sqlite` with a plain `Path.exists()` *before* constructing `KnowledgeStore` (issue #50):** when `--domain` is given and the file is absent (a never-tagged repo), error with a clear "no knowledge store — run `tag-domains` first" rather than constructing the store (which would create an empty DB and its dir as a side effect — issue #33) and then failing with a confusing empty-catalog "unknown domain". When `--domain` is omitted, never open the knowledge DB at all (behavior is exactly as today). Resolution accepts either form (issue #39): an exact `domain_id` slug match, or a **case-insensitive** display-name match against `list_domains()`. Because `unassigned` is a reserved `file_domains` value with no `domains` row (Milestone 2), name resolution special-cases it: `--domain "Unassigned"` (or `--domain unassigned`) resolves to the reserved slug `"unassigned"` directly, and `files_for_domain("unassigned")` / the Chroma `where={"domain":"unassigned"}` both work off `file_domains` without a catalog row. **If the argument resolves to no known domain (and is not the reserved `unassigned`), error with a clear message that lists the available domains (e.g. "unknown domain 'X'; run `legacylift-search domains` to list") — do not silently return zero results (issue #39), which is indistinguishable from a valid-but-empty domain.** Thread an optional `where` into `ChromaVectorStore.query(query_embedding, limit, where=None)` (pass it straight to `collection.query`). In `SearchEngine`, accept an optional `domain_id` **and the set of in-domain paths** — the CLI opens the knowledge DB, resolves the name to a `domain_id`, and passes both `domain_id` and `files_for_domain(domain_id)` (a `set[str]`) into the search call (`SearchEngine.__init__` today takes only `store, vector_store, embedder, config` — `search.py:37-47`, so this is a new parameter, threaded through `search(...)` rather than requiring `SearchEngine` to own a `KnowledgeStore`). The vector side passes `where={"domain": domain_id}` into `_vector_ranks`.

**The lexical drop happens in the fusion loop, not in `_lexical_ranks` (issue #23).** `_lexical_ranks` (`search.py:62`) returns only `chunk_id → rank` and has no `relative_path` to filter on. The main fusion loop already calls `chunk = self.store.get_chunk(chunk_id)` (`search.py:114`), which yields `chunk.relative_path`; drop any result whose `relative_path` is not in the passed-in in-domain path set there (this also naturally filters vector-side results that slipped through, keeping both sides consistent). The vector side (Chroma `where`) and the lexical side (path-set membership) stay consistent because Chroma's `domain` is a derived mirror of `file_domains` (the Milestone 5 invariant); a `manual` correction shows up on both sides once that file has been re-embedded or a `tag-domains` reconcile has run. When `--domain` is omitted, behavior is exactly as today.

**Over-fetch the lexical side under `--domain` to avoid recall starvation (issue #46, mechanics corrected by #49).** First, the search internals as they actually are — the sixth-pass #46 text mis-modeled them (issue #49): **neither arm is sized to `limit`.** `_vector_ranks` (`search.py:51`) fetches `self.config.vector_candidates` rows (default **40**) and `_lexical_ranks` (`search.py:62`) fetches `self.config.lexical_candidates` rows (default **40**, `config.py:170-171`); the fusion loop fuses both candidate pools and only *then* truncates to `effective_limit` (default 10, `search.py:139-140`). So even **unfiltered** search already over-fetches 40 candidates per arm — it does **not** "request exactly `limit`." And `_lexical_ranks` takes **no `limit` argument** today; its pool size is the config value, which is the real over-fetch lever (not `limit`). Under `--domain`, the vector arm is pre-filtered by Chroma's `where` *before* `n_results`, so its `vector_candidates` hits are all in-domain; the lexical arm is not — it fetches `lexical_candidates` **global** FTS5 hits and the in-domain drop happens *after*, in the fusion loop (`search.py:114`, where `chunk.relative_path` is available). For a small domain almost all of those global hits are out-of-domain and discarded, starving the lexical contribution and collapsing results toward vector-only. Mitigate by **scaling the lexical candidate pool** when (and only when) a `--domain` filter is active: give `_lexical_ranks` (and `store.search_lexical`) an optional count override — it has none today — and request an enlarged pool, e.g. `lexical_candidates × k` (k≈5, capped at a sane ceiling), so that after the in-domain drop roughly `lexical_candidates` in-domain rows survive to fuse. Unfiltered search uses `lexical_candidates` unchanged. (This is a recall improvement, not a correctness fix — the drop itself is already correct; the acceptance term below should be chosen to appear in only a *few* in-domain files so the starvation is actually exercised.)

**Unverified assumption — the vector arm is *not* over-fetched, on the premise that Chroma's `where` fills `n_results` from the in-domain set (issue #57).** The asymmetry above (enlarge the lexical pool, leave the vector pool at `vector_candidates`) rests on Chroma applying `where` as a true pre-filter that returns a *full* pool of in-domain hits. The "all in-domain" half is guaranteed — a `where` query never returns an out-of-domain row. The "full pool" half is **not** verified for the pinned chromadb 1.5.9 and is a known soft spot: HNSW-plus-metadata-filter can return **fewer** than `n_results` even when more in-domain matches exist, because the approximate graph walk may not reach enough filter-passing neighbors in a large collection. On the fixture (tiny, everything in-domain of its domain) this never bites; at ctcm scale the vector arm could itself under-fill, with no over-fetch analogue to compensate — silently narrowing `--domain` vector recall. This is the exact class of version-specific behavior the `update`-merge probe pinned down; before the first at-scale ctcm run, probe a filtered `collection.query(..., where=...)` on a large collection to confirm it fills `n_results`, and if it does not, apply the same pool-scaling lever to the vector arm (raise `vector_candidates` under `--domain`, or over-fetch and truncate). Until probed, treat vector-side in-domain recall at scale as unconfirmed rather than assumed.

**But over-fetching alone does not restore lexical weight — the in-domain survivors must be re-ranked densely before RRF (issue #54, revises #23 for the filtered case).** RRF scores each hit `1/(k + rank)` with `k = rrf_rank_constant` (default **60**, `config.py:172`), and `_lexical_ranks` assigns `rank = i+1` = the hit's position in the **global** FTS5 list (`search.py:74`). Under `--domain` the vector arm is re-densified to in-domain ranks 1..N by Chroma's `where` (it pre-filters *before* `n_results`), but if the lexical drop stays in the fusion loop (#23) the surviving in-domain lexical hits keep their **global** ranks — so an in-domain hit at global position 150 contributes `1/(60+150) ≈ 0.0048` instead of the `1/(60+2) ≈ 0.016` its in-domain position deserves (a ~3.4× suppression), and enlarging the pool pushes those global ranks *deeper*, not shallower. The net effect is that the over-fetch pulls the in-domain lexical hits into the pool but they almost never crack `effective_limit` (10), so `--domain` search stays effectively vector-only — the exact failure #46 set out to fix. Therefore, **when `--domain` is active, filter the lexical results to in-domain and re-enumerate them 1..N *before* they enter RRF**, so their fusion weight matches the (already-dense) vector arm. This requires `relative_path` at the lexical stage: either give `_lexical_ranks` the in-domain path set and have it look up each hit's `relative_path` (via `store.get_chunk`, as the fusion loop already does at `search.py:114`), keeping only in-domain hits and enumerating the survivors densely; or do the equivalent filter-then-re-rank in a dedicated pre-pass. This **augments #23 for the `--domain` path**: the lexical arm is now filtered *and re-ranked before* RRF (new), while the fusion-loop drop from #23 **stays in place** as the vector-side safety net (it discards any vector hit that slips through Chroma's `where`). "Supersedes" refers only to *where the lexical filter lives* — it moves out of the fusion loop and into a pre-RRF pass; it does **not** mean the fusion-loop drop is removed. Concretely, after this change: lexical hits are already in-domain and densely ranked when they reach RRF, and the fusion loop's drop is a no-op on them but still active on vector hits. Unfiltered search is unchanged — no re-ranking, no pre-filter, ranks stay global for both arms, and the fusion-loop drop does nothing (empty in-domain set ⇒ not applied).

**Implementation caution — don't `get_chunk` each lexical candidate twice (issue #54).** The re-rank needs each lexical candidate's `relative_path` *before* RRF, but the fusion loop already looks the chunk up (`self.store.get_chunk(chunk_id)`, `search.py:114`). Under the enlarged `lexical_candidates × k` pool a naïve implementation would resolve every candidate once to filter/re-rank and again in the fusion loop — doubling the lookups on the exact path that just grew k-fold. Resolve the in-domain filter membership cheaply instead: the CLI already passes the in-domain **path set** (`files_for_domain(domain_id)`), but the lexical stage has only `chunk_id`, so either (a) add a batched `chunk_id → relative_path` lookup to the store (one query for the whole pool) and filter/re-rank off that, or (b) do a single `get_chunk` pass whose results are cached and reused by the fusion loop rather than re-fetched. Prefer (a) — a `SELECT id, relative_path FROM chunks WHERE id IN (…)` is one round-trip and avoids materializing full chunk rows just to read a path. Either way, the extra work fires **only** when `--domain` is active; the unfiltered path must keep its current single-lookup-in-the-fusion-loop shape with no added queries.

Acceptance (fixture), two parts — the second is load-bearing and is the only part that exercises the #46/#54 recall fix:

1. **Filtering correctness (catches an absent `--domain` filter, i.e. #23):** `search "<term that appears in both src and database files>" --domain "Data Layer"` returns only `database/**` results; the same query without `--domain` returns results spanning both. Verify a result's `relative_path` prefix matches the requested domain.
2. **Lexical recall under `--domain` (issue #58 — catches an absent/broken #54 re-rank; without this the milestone can pass with the recall fix entirely omitted).** Note that part 1 **passes with #46/#54 removed**: the #23 fusion-loop drop alone keeps results in-domain, so a `--domain` search that has silently degraded to vector-only still returns only `database/**` rows and still satisfies part 1. To actually pin the fix, pick (or add to the fixture) a term that (a) appears **lexically** in a `database/**` file in a way that is **not** semantically close to the query embedding — e.g. a distinctive identifier or token inside a SQL comment — and (b) appears in **many** `src/**` files so the global FTS5 list is dominated by out-of-domain hits and pushes the in-domain hit to a deep global rank. Assert that under `--domain "Data Layer"` that specific `database/**` lexical match **appears in the returned top-N**. With the dense pre-RRF re-rank it surfaces (in-domain rank ≈ 1–2 ⇒ RRF weight `1/(60+2)`); without it, its deep global rank (`1/(60+150)`-class weight) keeps it out of the top-N and this assertion fails. This is the assertion that distinguishes "filter works" from "filter *and* recall work," so it must be a hard check, not a manual eyeball.


### Milestone 7 — `validate` domain-freshness axis

Goal: make "the file set has moved ahead of the domain tags" a distinct, loud, observable state — while treating the reserved `Unassigned` bucket as a legitimate, *accepted* gap, not as staleness.

Conceptual model (this is the resolution of the untagged-vs-unassigned distinction; the two are **not** the same and only one drives the verb):

- **untagged** — a discovered file with **no** `file_domains` row at all. Means no tag pass has accounted for it yet. **This is the staleness signal.**
- **unassigned** — a discovered file whose `file_domains` row is the reserved `unassigned` domain. This is an *accepted* gap, written **only** by `tag-domains` (an explicit, assess-driven review event). It is **not** staleness — it is reported as coverage information.
- The indexer's 7-Auto (Milestone 5) writes `glob` rows for files that match a domain and leaves non-matching new files **untagged**; it never manufactures `unassigned` rows. So a glob-matchable new file becomes fresh automatically on reindex (zero-touch), while a genuinely new/unclassified file stays untagged → `stale` until an assess/`tag-domains` pass reviews it. This is exactly the "goes loud when new, unclassified files appear" behavior promised in the Purpose.

At the end of this milestone, `legacylift-search validate --repo-root <repo>` prints, in addition to the existing index-freshness line, a domain line — stale form:

    domains: stale · coverage 88% · 12 unassigned · 3 manual · 3 untagged (1 glob-matchable, 2 need assess) · assess run 2026-07-17T15:04:05Z-polyglot

and fresh form (every discovered file has a row):

    domains: fresh · coverage 88% · 12 unassigned · 3 manual · assess run 2026-07-17T15:04:05Z-polyglot

Work: in the `validate` command, after the existing checks, compute against the discovered file set (`discover_source_files`). **First probe `knowledge.sqlite` with a plain `Path.exists()` (issue #33): if it is absent, report `domains: missing` and return — do not construct a `KnowledgeStore` to find out it is missing, because construction creates the file (and its dir) as a side effect, defeating the check and littering an empty DB into an un-tagged repo.** When the file exists, open it with the normal `KnowledgeStore` constructor (it has **no** read-only mode — issue #25/#33; the earlier "open the knowledge DB read-only" wording is dropped) and compute:
- `rows` = `file_domains` keyed by `relative_path`; `untagged` = discovered files with no row.
- Split `untagged` into **glob-matchable** (would match a stored glob via the shared `DomainTagger.resolve_file_domains`) vs **need-assess** (match none) — this uses the globs already in the `domains` table and tells the user the remedy (run `index` for the former, re-run assess/`tag-domains` for the latter).
- **All count buckets are computed over `rows` restricted to the discovered set — `rows_present = { p: r for p, r in rows.items() if p in discovered }` — not over the raw `file_domains` table (issue #42).** After a `tag-domains` run the reap (#38/#42) already guarantees `file_domains ⊆ discovered`, and the indexer likewise reaps deleted paths (#45), so `rows_present == rows` in the common case; the intersection is a cheap, defensive guard for the window between reconciles (e.g. after a non-reindexing external SQLite edit). Without it, a `file_domains` row for a file no longer on disk would inflate the numerator: `classified` (and thus `coverage`) could exceed 100% and contradict a simultaneous `stale`/`untagged` state (`validate` reporting `stale · coverage 200%`).
- `classified` = `rows_present` whose `domain != 'unassigned'`; `unassigned` = `rows_present` whose `domain == 'unassigned'`; `coverage = classified / max(1, |discovered|)`. By construction the partition is exact: `classified + unassigned + untagged == |discovered|`, and `coverage ∈ [0, 100%]`.
- `manual` = `rows_present` whose `source == 'manual'`. (Counting over `rows_present` keeps it consistent with the invariant above; since the reap removes `manual` rows for deleted files (#42), there are no orphaned manual rows to miss.)
- most-recent `assess_run_id` from `domains`.

Report `domains: stale` iff `untagged > 0`; `domains: fresh` when `untagged == 0` **regardless of the unassigned count** (an unassigned row is an accepted gap and never forces stale); `domains: missing` when the `domains` table is empty **or `knowledge.sqlite` does not exist at all** (issues #19, #33 — never tagged; detect the absent file via `Path.exists()` before constructing, and never throw on it). Always show `coverage`, the `unassigned` count, and the `manual`-override count so a growing unassigned trend (new code that no domain claims) stays visible even while `fresh`, and so the operator is always aware that hand-set overrides exist (and are being honored, never overwritten). When `manual > 0`, `validate` appends an explicit note, e.g. `— 3 manual override(s) preserved; not overwritten by glob resolution`.

**Route the coverage gap to a fix (issue #48).** Reporting `coverage < 100%` is not enough — the gap must be *actionable*. When `unassigned > 0`, `validate` appends a concrete remedy that names the downstream process, not just the number: e.g. `— N file(s) unassigned (coverage gap); re-run modernize-assess with domain globs that cover them (or author a Shared/Common domain), then re-run tag-domains`. This closes the loop: the operator sees the gap on the always-visible coverage axis, is told exactly which process resolves it, and can enumerate the offending files with `legacylift-search search --domain "Unassigned"` (vector + lexical, now consistent per issue #44) or a `domains`-command listing before re-running assess. The freshness verb (`fresh`/`stale`) is unchanged — the gap lives on coverage, not freshness (see issue #2's resolution) — but it is no longer a dead-end number.

### Milestone 8 — `render-architecture`: derived `ARCHITECTURE.mmd`

Goal: generate the domain dependency diagram deterministically through a **single renderer**, and stop having assess emit the legacy-analyst's LLM-authored Mermaid (today Step 6 copies out "the Mermaid domain dependency diagram from the legacy-analyst", `modernize-assess.md:241-242` — issue #35) — while keeping the diagram a first-class deliverable of the assess run.

At the end of this milestone, `legacylift-search render-architecture [--repo-root <repo>] [--domains <domains.json>] [--output <path>]` writes a Mermaid `graph TD` built from domain nodes and inter-domain edges (`--repo-root` is required only when `--domains` is omitted — issue #27). Four design points resolve issues #12, #13, #27, and #28:

- **Output path (issue #12).** The command **defaults to stdout**; `--output <path>` writes a file. It does **not** default to `analysis/<system>/ARCHITECTURE.mmd` — that path is a `modernize-assess` convention keyed on the system-dir name (`analysis/$1/`, a sibling of the repo), which a `legacylift-search` command invoked with only `--repo-root <system-dir>` cannot derive. There is no `--system` flag. assess supplies its own path explicitly via `--output` (see below). Stdout is the always-computable default and is what the acceptance test exercises.
- **Source + timing (issue #13, Option B, single code path).** The renderer can source its nodes/edges from **either** a `domains.json` file (`--domains <path>`) **or**, when `--domains` is omitted, the SQLite `domains` + `domain_edges` tables. Both feed **one** `render_architecture_mermaid(domains, edges) -> str` function — assess never hand-authors Mermaid; it **shells out** to this command. This closes the sequencing gap: domains only reach SQLite after `tag-domains` (sequence `index → assess → tag-domains`), so at assess time SQLite is empty, but assess has just authored `domains.json` and renders from that. After `tag-domains`, re-running `render-architecture` **without** `--domains` regenerates the diagram authoritatively from the stored, tagged truth (cannot drift). The `--domains` form is the same parse/validate path as `tag-domains` (`load_domains_json`), so `display_order` is assigned identically (array index) and the two sources produce identical output for identical data.
- **Both sources are normalized to one shape before rendering (issue #36).** The SQLite source yields `DomainRecord` (which carries `display_order`) and `DomainEdgeRecord` (fields `from_domain`/`to_domain`); the `--domains` source yields `DomainsFile` domain entries (whose JSON has **no** `display_order` field) and edge entries (keys `from`/`to`, modeled as `from_`/`to_`). `render_architecture_mermaid` must receive a *single* uniform shape, so the CLI adapts the JSON source before calling it: **assign `display_order = array index`** to each domain (matching what ingest stores, so the SQLite render agrees), and **map the edge `from`/`to` onto the same field names** the renderer reads, **and default a missing edge `kind` to `""`** (issue #51) so it matches `domain_edges.kind`'s `NOT NULL DEFAULT ''` column — otherwise a JSON edge with no `kind` renders a different label than the same edge after ingest, breaking byte-identity (and, at ingest time, a `None` `kind` would violate the `NOT NULL` column). Without this the two renders are not byte-identical (or the JSON render has no sort key at all). **Also deduplicate the JSON edge list on `(from, to, kind)` before rendering (issue #56).** `domain_edges` has that triple as its PRIMARY KEY, so ingest silently collapses a repeated edge to one row; the `--domains` source, by contrast, iterates the JSON `edges` **array** verbatim. If assess ever emits the same `A→B/kind` edge twice (nothing forbids it — the edges mirror an LLM-authored Mermaid diagram), the SQLite render emits one arrow and the JSON render emits two, and the M8 byte-identity guarantee fails — invisibly, because the hand-authored fixture has no duplicates and the acceptance test would still pass. Dedup the JSON edges on the same triple the PK uses so both sources always agree. The renderer's parameter types are pinned in the Interfaces section.
- **Drop edges whose endpoints are not in the node set (issue #36).** `domain_edges` has no foreign key to `domains` (SQLite has none across the authored tables), and assess can author an edge to a domain it didn't list. Mermaid auto-creates a node for any unknown edge endpoint, which would inject a phantom node and break both the diagram and the byte-identical guarantee. `render_architecture_mermaid` must filter out any edge whose `from`/`to` is not among the emitted domain nodes (this also covers edges touching the excluded `unassigned` slug — issue #28 — as a subcase).
- **`--repo-root` is required only for the SQLite source (issue #27), and that source must existence-probe first (issue #50).** When `--domains` is omitted the renderer must open `knowledge.sqlite`, so `--repo-root` is required — and because `render-architecture` is a read-only `KnowledgeStore` consumer, probe `knowledge.sqlite` with a plain `Path.exists()` *before* constructing: if the SQLite source is selected but the file is absent (never-tagged repo), error with "no knowledge store — run `tag-domains` first" rather than constructing an empty DB (issue #33) and rendering an empty diagram. When `--domains` **is** given the renderer reads the file directly and never touches the knowledge DB, so `--repo-root` is **optional and unused** — make it an optional option (default `None`) and validate at runtime: if **both** `--domains` and `--repo-root` are absent, error with a clear message. This is what lets `modernize-assess` shell out with `--domains` alone (see Work): the assess argument `$1` is the *system-dir name*, **not** the resolved on-disk `legacylift-search` repo-root (per `modernize-assess.md` Step 3, the repo-root is the directory `$1` resolves to, e.g. `repos/ctcm/ctcm-api`), so passing `--repo-root "$1"` would be wrong — and it is unnecessary for the `--domains` render path anyway.
- **The reserved `unassigned` slug is never a node (issue #28).** `render_architecture_mermaid` filters out any domain whose `domain_id == "unassigned"` (and any edge touching it) before emitting nodes/edges. This is belt-and-suspenders: per Milestone 2, `unassigned` is a `file_domains` value with no `domains` row, so `list_domains()` already never returns it and `domains.json` never carries it — but the explicit filter guarantees the two sources stay byte-identical even if a future change ever materializes an `unassigned` catalog row.

The `Shared`/`Core` domain, if present, is rendered as a cross-cutting node (no dependency arrows implied). **Detection is by reserved slug (issue #20):** a domain whose `domain_id` is in the reserved set `{"shared", "core"}` (exact slug match, the same kebab-case slugs assess authors) is the cross-cutting node — deterministic and requires no schema flag. If no domain matches, nothing special happens; every domain renders as an ordinary node. (A `domain_flag`/`kind` column is a future extension if richer categories are ever needed — out of scope here.)

## Idempotence and Recovery

Every new command is safe to re-run. `tag-domains` uses `INSERT OR REPLACE` for authored tables (followed by a reap of authored rows absent from the current `domains.json` — issue #41) and manual-wins upserts for `file_domains` (followed by a reap of every undiscovered row regardless of `source` — issues #38, #42), so repeated runs converge to the same state and a re-tag that *removes* a domain (or a file) fully cleans it up rather than leaving an orphan. The indexer's 7-Auto resolution is a deterministic function of stored globs and the file list. `render-architecture` is a pure read-render. Creating either database is `CREATE TABLE IF NOT EXISTS`, so migrations are additive and repeatable.

Recovery: because `knowledge.sqlite` is separate and never deleted by `--reset`, a corrupted or unwanted **index** can be rebuilt freely without losing domains or manual corrections (`symbol_facts` lives in `index.sqlite` and is re-extracted by the rebuild, so no fact *information* is lost — only recomputed). A `--reset` rebuild re-stamps Chroma `domain` metadata from the surviving `file_domains` rows via the shared `_embed_and_upsert` path (Milestone 5), including when the rebuild is completed with `backfill-vectors`. If for any reason the vector side ends up without `domain` metadata (e.g. a rebuild that predates the Milestone 5 stamp, or a manually interrupted flow), run `tag-domains` once with the last `domains.json` to reconcile Chroma from the authoritative rows — no re-embedding. If the **knowledge** DB itself must be rebuilt, re-run `tag-domains` with the last `domains.json` (or re-run assess to regenerate it); manual corrections would need to be re-applied, so back up `knowledge.sqlite` before destructive operations on it. Keep `domains.json` around until ingest is confirmed, then it may be discarded.

Setting, changing, or **clearing a manual tag** (v1 has no correction UX — see the deferred-work note below): a manual tag is a `file_domains` row with `source='manual'`. To *clear* one and return the file to automatic (glob) classification, **delete the row** rather than editing `source` in place:

    DELETE FROM file_domains WHERE relative_path = ?;   -- in knowledge.sqlite

then run `tag-domains` once to reconcile — it re-resolves the freed file against the stored globs, writes the correct `glob`/`unassigned` row, and **re-stamps Chroma from that row** (no re-embedding). Two cautions: (1) a bare `UPDATE file_domains SET source='glob'` is **not** sufficient — it leaves the row holding the old manual domain and leaves Chroma pointing at it until a reconcile, so `DELETE` + `tag-domains` is the correct sequence; (2) `DELETE` is preferred over `UPDATE` because a freed-but-not-yet-reconciled file shows up as `untagged`/`stale` in `validate` (fails loud), whereas an in-place `source` flip reads as a plausible-but-wrong `glob` row (fails silent). The same asymmetry applies to *setting* a manual tag (insert the row, then reconcile). Because both operations are raw-SQL-plus-reconcile in v1, the ergonomic `set-domain`/`clear-domain` verbs that fold the SQLite write and the targeted Chroma restamp into one atomic command are recorded as deferred correction tooling.
